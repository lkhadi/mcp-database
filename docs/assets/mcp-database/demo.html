MCP Database Companion Skill

This guide explains the companion skill, its separate server dependency, and the recorded demos. The skill provides instructions for an AI agent; the mcp-database server provides the database tools.

What the skill does

  • Discover configured MySQL and PostgreSQL databases.
  • Inspect schemas, columns, keys, and relationships before writing SQL.
  • Produce SQL reports with explicit connection and database targets.
  • Guide authorized data corrections through previews and result checks.
  • Handle uncertain query outcomes without blindly replaying submitted SQL.

What you need

An agent that can load the skill and call a configured local MCP server; a compatible, locally built mcp-database checkout; Node.js 18+ and npm; and your own database access. SSH access is needed only when your connection uses a tunnel. Specific agent integrations have not all been tested.

The server setup is documented in the server repository. The skill ZIP includes references/setup.md with build-verification guidance. Do not assume the package name db-access is an npm-published installer.

Load and use the skill

Use your agent or marketplace's supported skill-loading mechanism. Skill delivery does not install the server or configure database credentials. Keep credentials in your local server configuration.

Once the MCP tools are available, ask the agent to discover databases and specify the connection, database, schema, and table you want to inspect. For reporting, state the filters and totals you need. Authorize data changes separately and use a database account with privileges appropriate to the task.

Tools and limits

The server exposes list_databases and execute_sql. Every SQL call requires a connection, database, and exactly one statement. Pooled calls do not share a guaranteed database session, so do not split transactions or depend on temporary tables across calls.

Keyword blocking does not enforce read-only access; use database privileges for that. Displayed results may be truncated. A connection failure after submission can leave the outcome unknown; reconcile the database state rather than assuming rollback or retrying blindly.

Verify a server build that enforces single-statement calls and avoids automatic replay after submission. Older server builds may behave differently. A successful connectivity check alone does not establish these guarantees.

About these demo images

These images present actual responses captured through the MCP SDK from the locally built server and an isolated PostgreSQL 18.3 database. Six fictional customers and twenty fictional orders were seeded before the demonstration. The recorded workflow used a SELECT-only role, with read-only transactions enabled. The images are formatted transcript reports, not screenshots of a third-party agent app or an end-to-end marketplace installation.

The accompanying mcp-demo-transcript.json contains the executed calls and original responses. demo-fixture.sql contains the fictional data. The local database was stopped after capture. The examples demonstrate PostgreSQL; they do not constitute a live MySQL test.
